# KnownFaces release operations

Use the [production deployment runbook](production-deployment.md) for the current IaC sequence, including the unbound foundation, scoped role grants, package publisher, Linux HCM containers and reviewed environment approval. The operational checks below also apply to installations made with these scripts.

The local service runs independently on 8093. The private pilot uses a different process and synthetic volume on 8094. The proposed edge is one Linux B1 App Service with a Node gateway, one Azure Relay Hybrid Connection, and a private blob container for a small code ZIP. The site uses its Azure-provided HTTPS hostname as the OAuth resource host. No application insights, body tracing, access logs, gallery, face images or audit records belong at the edge. ARM activity records for resource changes are expected. The SSH/Caddy example remains an independent alternative.

## Run checks

Pull requests and main builds run credential-free tests on GitHub-hosted Ubuntu. The local equivalent is `python -m scripts.ci`. Install Python 3.13, the packages in `requirements.txt`, pytest 9.2.0, Node 24, OpenSpec 2.1.1, Bicep 0.41.2 and Linux Docker. Keep camera IDs, access credentials, images, database files and release approval records out of source control.

## Azure setup and authority

Obtain approval for a dedicated existing or new resource group, region, unique site name and budget. Provisioning incurs roughly **USD 13.14/month** for one Linux B1 even while blocked. One continuously connected Relay listener adds about **USD 9.78/month** including 5 GB, for about **USD 22.92/month** before storage, traffic overages, taxes and runner costs. Blob storage and transactions for gateway code are additional. Reprice the chosen region and agreement before provisioning. [Linux App Service pricing](https://azure.microsoft.com/en-us/pricing/details/app-service/linux/) · [Relay billing example](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-pricing-billing)

- An authorized tenant/RBAC administrator separately creates two distinct workload identities and the dedicated group, registers Microsoft.Web, Microsoft.Relay and Microsoft.Storage if needed, and configures protected environments on main. Preview federation uses subject `repo:OWNER/REPO:environment:knownfaces-preview` with issuer `https://token.actions.githubusercontent.com` and audience `api://AzureADTokenExchange`. Set environment-scoped GitHub secrets for `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `KF_GROUP`, `KF_LOCATION`, `KF_SITE`. Set the repository variable `KF_AZURE_ENABLED=true` only after the preview trust and protected main are in place. Keep group, subscription, region and site identical across environments. These identities are independent of the MCP client's OAuth registrations.
- Assign the preview principal RG resource reads plus `Microsoft.Resources/deployments/whatIf/action` and validation as needed. Use Azure CLI 2.76+ with working `--validation-level ProviderNoRbac`; verify the flag on the actual CLI and validate the role with the actual providers. Exclude create, key listing, data-plane writes and RBAC administration. If preview needs a write grant or cannot resolve a value, stop for review. The deploy principal needs RG deployment read/what-if/validate/write and read/write for the declared Web, Relay and Storage types. ARM resolves the entity Send key for the site binding. Restrict key-reading authority to the `edge-send` rule where possible, verify effective permissions, and exclude namespace management keys, Listen key access, role assignment and subscription-wide roles. Have the security administrator stage any required scoped role assignment under a separate approval. Give the site identity Blob Data Reader on the gateway container after blocked provisioning. Give the deployment verifier read-only access there and a separate operator limited upload rights. No deployment identity needs gallery access. [ARM validation levels](https://learn.microsoft.com/en-us/rest/api/resources/deployments/what-if) · [Managed identity for package access](https://learn.microsoft.com/en-us/azure/app-service/deploy-run-package)
- **Keep CI apply disabled by default.** Only create the independent deploy federated subject `repo:OWNER/REPO:environment:knownfaces-apply` after verifying private environment required reviewers, main-only deployment policy, prevented self-review and the independent reviewer/digest check before Azure login. Test rejection with an unprivileged account. Then set the repository variable `KF_PROTECTED_APPLY=verified`. A variable alone cannot authorize apply. If independent reviewer protections are unavailable, omit deploy federation and run apply on an independently approved operator workstation. [GitHub environment protection availability](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

## Preview, provision and publish

1. **Preview authorization** permits ARM what-if on the selected RG. Dispatch the Azure workflow with `operation=preview` and `preview_target=blocked`, or use the command below in a clean checkout of the reviewed main commit. Keep CLI debug, HTTP tracing, shell tracing and sensitive diagnostics disabled. The tool captures provider output privately and emits the resource types, change categories, safe field labels and hashes. Deployment target values stay in the protected environment. Reviewers confirm the target privately and use the digest to bind approval. Use the same environment values on the package publisher. Review that alongside the actual template, parameters, package contents and expected changes. Unexpected modifications, uninspectable private-field changes, unsupported/ignored resources, unresolved expressions, warnings or missing provider detail require a new investigation and review. ARM what-if is predictive and cannot lock the resource group. Use an exclusive change window, including for manual operations.

   ```sh
   python -m scripts.azure_release preview --target blocked --record /private/review.json
   ```

2. **Blocked provision approval** covers one specific commit, subscription/group, parameters, template/package hashes, reviewed plan digest and expiry. A separate reviewer records these and the preview run ID. In protected CI dispatch `provision-blocked` with that prior preview run and approved digest. Outside CI use the same command below only after independent approval and time-limited deployment access. Both paths recompute the plan and stop on mismatch. This creates the billed plan, HTTPS-only site with public access disabled and deny-by-default main/SCM, private release container, Relay entity, separate Send/Listen policies and its 8094 binding. No package bytes or home listener are installed by this operation.

   ```sh
   python -m scripts.azure_release provision-blocked --approved /private/review.json --digest "$APPROVED_DIGEST"
   ```

3. **Package publication approval** permits uploading just the reviewed deterministic ZIP to the private container. Verify publicNetworkAccess is Disabled, main and SCM default Deny, external GET/POST to the intended site returns the platform block (normally 403), and the home listener is stopped. Record those checks before and after upload, while holding the exclusive change window. Build with `python -m scripts.package_gateway /private/packages`. Match the archive SHA-256 with the reviewed packageSha. Publish using the operator's short-lived Entra login, content-addressed name and a create-only condition. Verify the downloaded bytes match and grant the site identity its container-scoped read separately. Publishing cannot change site settings. A missing package, failed digest check or site blocked-state check stops activation. Disable ongoing write access after publication. Never put SAS URLs or publishing credentials in settings or GitHub.

   ```sh
   python -m scripts.publish_gateway --approved /private/review.json --digest "$APPROVED_DIGEST"
   ```

## Home listener, synthetic activation and cutoff

1. **Home setup approval** covers only the isolated synthetic pilot volume and dedicated 8094 MCP process. Follow the [remote MCP setup](remote-mcp.md). Keep recognition and management switched off, populate only a synthetic subject and owner-mapped synthetic camera, disable webhooks and leave continuous capture off. On the HCM host resolve `knownfaces-mcp.invalid` exclusively to its own loopback and test `knownfaces-mcp.invalid:8094` with the canonical Host header. Verify its dedicated service identity/network policy can reach only that application destination plus required outbound Relay/TLS infrastructure. If connection confinement or DNS interception cannot be verified, keep the listener stopped. App Service must issue a hostname lookup for Hybrid Connections. A missing binding must fail DNS. No public DNS record or home router mapping is needed. [Microsoft Hybrid Connections and HCM guide](https://learn.microsoft.com/en-us/azure/app-service/app-service-hybrid-connections)
2. Retrieve only the entity-level `home-listen` credential on the home host through an approved private channel. Import it with the supported HCM secret-entry method, avoiding shell history, process argument capture and transcripts. Use the desktop HCM connection-string dialog on supported Windows if the installed Linux CLI cannot securely receive the secret. Protect HCM configuration with host ACLs. Keep the Listen credential off runners and out of deployment outputs. The automated Linux installation uses the pinned HCM CLI's `add-from-file` command inside its dedicated container. The Azure binding gets only `edge-send`. Never use the namespace root policy. One authorized HCM instance establishes outbound TLS on 443. Validate target port, DNS behavior, HCM version and regional App Service support before opening the pilot.
3. **Activation requires a new preview and separate approval** for `preview_target=synthetic` at the same intended resource URL. Review the blocked checks, package identity, HCM target, grant setup, sanitized logging and synthetic home policy. Only the existing App Service should change. With the new run ID and digest, dispatch `activate-synthetic`, or manually run `python -m scripts.azure_release activate-synthetic --approved /private/activation.json --digest "$ACTIVATION_DIGEST"` using independently approved temporary deployment access. This rechecks the blocked main/SCM configuration, verifies the Azure blob bytes, repeats what-if, opens HTTPS for the dedicated site and enables its three-path gateway. SCM stays denied. Verify the real App Service default hostname matches both gateway and protected-resource metadata. Platform-reserved paths can return platform responses; no unrelated request may reach the home listener. Check the exact OAuth challenge, POST/GET/DELETE handling, SSE time to first event, heartbeats, idle/platform timeouts, disconnect, relay outage, local operation and logs. Stop immediately on unexpected forwarding, sensitive logs or buffering.
4. **Connector acceptance** requires a private ChatGPT connector, dedicated Entra API/client registrations and approved redirect URI. Verify protected-resource and issuer discovery, predefined client configuration, authorization code + S256, requested resource, audience and read scope. Make one synthetic history read, then one denied edit and verify unchanged names, samples, sightings and edit receipts. Verify refresh after token expiry. Keep the local audit, redact credentials and use no household images. Confirm that the issuer metadata advertises S256 for the actual connector. If direct OAuth fails, record the exact stage, sanitized error and correlation ID; only then consider an isolated adapter with separate resource binding and scopes. [Pilot sequence](remote-mcp.md)
5. **Immediate cutoff:** stop the dedicated HCM service (`sudo systemctl stop hybridconnectionmanager.service` on a dedicated Linux listener) and stop only the pilot's `remote-mcp` process. Confirm no connected listener and that home 8093 still works. If an emergency cloud block is separately authorized, set App Service public network access Disabled immediately. Rotate/revoke affected entity keys and OAuth grants under their own approvals. For durable rollback preview `blocked` against the actual current state and apply `provision-blocked` with its new approval; verify the site is blocked, SCM denied and the gateway closed. Retain the local gallery and local audit. Deleting resources to end billing or disposing of the synthetic gallery requires separate approval.
